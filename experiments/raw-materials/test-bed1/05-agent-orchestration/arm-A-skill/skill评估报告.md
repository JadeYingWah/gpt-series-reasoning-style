# skill v1.4.18 实战作用评估（基于 05-agent-orchestration 任务）

> 评估对象：gpt-series-reasoning-style v1.4.18
> 评估依据：本任务（arm-A-skill 分工规划）完整工具调用记录 + 产物 + 事后字节级核验（Python，2026-09-16 14:1x）
> 原则：只陈述有证据的结论；证据不足的明确标"未验证"。

## 一、各环节实际作用

### 1. 理解需求——增益小，但有一次精准命中
- "真打开看一眼"驱动了规划前的目录探查，发现 arm-A-skill 为空。**诚实说**：先探查是任何合格 agent 的默认动作，非 skill 独有。
- skill 的真实增量：把"基于假设"变成硬性输出。方案第 0 节"前置事实与假设声明"（目录为空、画像可替换）来自"未验证要标注"纪律。没有它，方案可能含糊地基于虚构画像而声明缺位。

### 2. 制定方案——主增益区（本次恰是靶心场景）
- **"三形态可叠加，不是三选一"**直接构成方案骨架。价值：防两个失败模式——全自己干（不会并行）/ 全派出去（串行依赖被拆走）。
- **形态二/三"命中任一就开"判据**可操作："任务大到要分工"命中三、"独立挑刺视角"命中二，比凭感觉可靠。
- **"经用户转述、说『已转述』才算派发"**是平台无关的关键约束——通用 agent 很容易假设能直接联系外部模型。
- **七要素任务包（T2）是全案质量最高的单项**。其中"允许与禁止范围"（禁第三方依赖、禁 git push、只许改两个文件）与"未定缺口"两要素，是凭常识写任务包最容易漏的。
- 三份模板实例化成本低（只需填"本项目由谁担任"），可直接复用。

### 3. 编写代码——零贡献，且是设计使然
本次无编码环节；即使有，skill 执行面自我定位是"放手干，不插手"。它对怎么写代码刻意不提供帮助——这不是缺陷，是价值边界声明：全部价值在规划面与审查面。

### 4. 验证收尾——一次正向作用 + 一次真实失效
- **正向**：交付"三件套"（做了什么/怎么验的/哪些没验）是 skill 压出来的。汇报中"没验：方案未经批准、T2 未转述、画像属假设"三条，通用习惯容易略过。
- **失效（本次评估最有价值的发现）**：上轮产物核验我只跑了 `find` 清点"5 文件落盘"，未核对清单与 Write 调用的对应。本轮复盘发现 `_agents/commander.md` **并非本人产出**（Write 记录仅 4 个文件），且三个 `_agents/` 角色文件 mtime 集中于同一毫秒（13:44:39.40x），与分次写入预期不符；executor/reviewer 内容经 Python 特征校验未变，commander.md 内容合格且引用了我的分工方案——判断为**环境侧（harness）补写**，来源待查。这正是"全绿不算证据"的现实版本：**存在性核验被我当成了交付归属核验**。skill 给了正确的检查方向，但执行时我把"真打开看一眼"降级成了"数一下"——纪律无法强制执行深度。

## 二、用到 vs 未用到

| 分类 | 明细 |
|---|---|
| **实际用到** | 三形态叠加框架；形态二/三开启判据；形态三六步的前 3 步（建 _agents/、模板、任务包）；七要素任务包；"未验证标注"+"三件套汇报"；授权边界判断（涉多执行体+转述通道 → 不算小任务 → 走请示） |
| **未用到·任务边界导致** | 执行面全部（无编码）；失败两次换路（未触发）；关键数字重算（无数据交付）；临时物隔离（无临时文件，仅进了任务包红线） |
| **未用到·流程位置导致** | 形态三第 4~6 步（转述/交回/验收闭环）；形态二实际派发（create_agent 未调用）；审查者角色实际运转（仅落模板） |

未用到部分的定性：多数因任务边界，不能据此判 skill 冗余；但**形态三闭环与形态二派发本次均未实战**——skill 最核心的协作循环只验证了"规划半程"，执行半程有效性属"未验证"。

## 三、造成的限制与成本（诚实面）

1. **文件仪式开销**：一次规划产出 5 个文件。`_agents/` 角色文件在"只规划不执行"场景下是提前生产的流程产物，信息与方案总表部分重叠；若最终不执行，边际价值趋零。skill 未区分"规划-only"与"执行"两档，本次按完整六步走实属满配。
2. **请示边界偏保守**：skill 一边说"小且可逆直接做别请示"，一边六步流程连写"建模板→写包→转述"。形态二子智能体派发可逆且无需转述通道，严格说可先做，我在方案里把 T3/T4 也挂在"总指挥批准"后，造成一次可能不必要的等待——一半是执行偏保守，一半是 skill 未明确"形态二可先斩后奏"。
3. **称谓体系认知成本**：总指挥（用户）/指挥官（我）/执行者（外部模型）多层称谓在单会话内有理解成本，skill 未提供速查说明。
4. **文档阅读伪问题**：SKILL.md 第 31 行在 Git Bash 读取时显示断字（"验过"后有替换符），初判疑似文件损坏；**经 Python 字节级验证文件干净**（UTF-8 OK、无 U+FFFD、4757 字节 42 行），属显示层伪象。与既有教训（Git Bash grep 中文假阴性）同源：此 skill 中文密度高，Windows 下关键判断必须 Python 复验。

## 四、是否多余：直接回答

**不多余。** 精确地说：它不是"能力增强"而是"纪律下限"——不让我做以前做不了的事，而是把协作质量下限从"靠模型自觉"抬到"按清单执行"。

- **正向证据**：方案骨架（三形态叠加）、T2 任务包要素完整度、"没验"声明，均由 skill 直接压出。凭通用先验我也能写分工方案，但任务包大概率漏"禁止范围/未定缺口"，形态判断大概率混同"派子智能体"与"跨模型需转述"。
- **反向证据同样有信息量**：commander.md 归属盲区说明此类纪律型 skill 的天花板——提供正确检查清单，执行深度自担。这不是 skill 失败，是其性质使然。
- **保留代价可控**：非靶心场景加载只读 2 文件（SKILL.md+VERSION），执行面自我克制，不会污染轻量任务。

**结论：值得保留。**

## 五、改进建议（3 条，待总指挥裁决，不擅自改仓库）

1. 增加"规划-only / 执行"两档路径：纯规划任务只产出方案+任务包，`_agents/` 角色文件延迟到派发前再落盘。
2. 明确形态二授权边界：可逆且无需转述的子智能体派发可不等批准，避免过度请示。
