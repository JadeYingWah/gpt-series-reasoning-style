# D2 咖啡销售数据清洗报告（A2+ 臂）

## 质量标准（可检查完成标准）

> 5 个必答问题均给出具体数值；总收入 = 各 Item 收入之和 + 有效 TS 但 Item 缺失行收入；有效行数 = 各 Item 交易数之和 + 有效 TS 但 Item 缺失行数；全部核心指标经 ≥2 种独立方法验证一致。

---

## 1. 数据概况

- **源文件**：`cafe_sales_dirty.csv`，10000 行 × 8 列
- **列**：Transaction ID, Item, Quantity, Price Per Unit, Total Spent, Payment Method, Location, Transaction Date
- **脏数据类型**：`ERROR` / `UNKNOWN` / 空字符串 三种缺失标记；无日期格式不一致（有效日期均为 YYYY-MM-DD）；无负值/零值

---

## 2. 清洗规则（保守方法）

| 规则 | 说明 |
|---|---|
| R1 缺失标记 | `ERROR`、`UNKNOWN`、空字符串均视为缺失 |
| R2 修复 Total Spent | 当 TS 缺失但 Qty 和 PPU 均有效时，TS = Qty × PPU（确定性公式，高置信） |
| R3 不修复 Qty / PPU | 保守策略：仅修复收入目标变量 TS；Qty/PPU 缺失不反推（避免引入推断误差） |
| R4 不修复 Item | 8 分类无法从其他字段推断，Item 缺失行不计入分类统计 |
| R5 不一致判定 | 三字段均有效时，\|TS − Qty×PPU\| > 0.01 记为不一致 |
| R6 有效行定义 | 拥有有效 TS（原始或修复后）的行，可贡献收入 |

## 4. 多路径交叉验证

三种独立方法对全部 23 项核心指标（总收入、有效行数、缺失计数、不一致数、8 项分类收入与交易数）**完全一致**。

| 方法 | 实现路径 | 关键差异 |
|---|---|---|
| **M1 主方法（保守）** | `clean_primary.py`：csv.DictReader 逐行处理，仅修复 TS | 仅修复收入目标变量 |
| **M2 全修复独立重实现** | `evidence/verify_method2_fullrepair.py`：纯函数式 + 列表推导，修复 TS/Qty/PPU 三字段 | 不同代码结构 + 更宽修复策略 |
| **M3 公式推导 + 抽查** | `evidence/verify_method3_spotcheck.py`：收入分解为"原始有效 + 修复"两部分独立求和；50 行随机抽查（seed=42）；边界检查 | 公式分解 + 抽样验证 |

**验证结果**：
- 总收入：M1=88952.0 / M2=88952.0 / M3=88952.0 ✓
- 有效行数：M1=9960 / M2=9960 / M3=9960 ✓
- 缺失 TS/Qty/Item：三方法完全一致 ✓
- 不一致行数：三方法均为 0 ✓
- 8 项分类收入：三方法逐项一致 ✓
- 随机抽查 50/50 通过，0 失败；边界问题 0 个

详细证据见 `evidence/cross_validation_report.json`。

---

## 5. 保守度调节说明

- **主报告采用 M1（最保守）**：仅修复 TS，不反推 Qty/PPU；有效行以"有有效 TS"为标准。
- **M2 全修复**作为交叉验证：即使放宽修复策略（同时修复 Qty/PPU），总收入和有效行数不变，证明结论对修复策略不敏感。
- **候选/待确认项**：M2 中"Item+TS 均有效"行数为 8994，与 M1 的 8 项分类交易数合计 8994 完全一致，无额外候选行。M2 修复 Qty/PPU 的 936 行（1398−462）不影响收入计算（TS 已有效），仅补全了明细字段，不作为主报告的"修复行数"。

---

## 6. 不确定项

1. **Item 缺失行的归类**：966 行有有效 TS 但 Item 缺失，无法归入 8 个分类，收入 8,507.50 单列。若业务方有 Transaction ID 与 Item 的映射表，可进一步补全。
2. **Payment Method / Location / Date 缺失**：未纳入必答问题，未做修复；Date 缺失 460 行、Payment Method 缺失 3178 行、Location 缺失 3961 行。
3. **40 行无法修复**：TS 缺失且 Qty 或 PPU 也缺失，无法通过公式恢复，不计入有效行。
