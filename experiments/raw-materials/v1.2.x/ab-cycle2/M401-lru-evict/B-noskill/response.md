## 2. 改了什么

原实现有两处缺陷，二者叠加导致淘汰顺序不符合 LRU：

1. `get()` 命中后不更新使用顺序 —— 被访问过的 key 无法变成「最近使用」。
2. `put()` 淘汰时取 `self.order[-1]`（列表尾 = 最近使用），淘汰了**最新**的 key，
   而正确语义应淘汰 `self.order[0]`（列表头 = 最早使用 = 最近最少使用）。

修复后的关键行（`lru_cache.py`）：

- `lru_cache.py:14-15` —— `get()` 命中后 `remove` + `append`，把 key 移到队尾（最近使用）。
- `lru_cache.py:20-22` —— `put()` 覆盖已存在 key 时同样刷新顺序（覆盖写也算一次使用）。
- `lru_cache.py:25-27` —— 淘汰目标由 `self.order[-1]` 改为 `self.order[0]`，并把 `order.remove(victim)`
  换成 `self.order.pop(0)`。

公开接口未改动：`LRUCache(capacity)` / `get(key)` / `put(key, value)` 名称与签名逐一核对未变
（见下 §3.6）。类内公开方法集合仍为 `['get', 'put']`，未新增任何方法。

## 4. 不确定项 / 需要说明的地方（未验证或与任务描述有出入）

### 4.1 ⚠️ task.md 给出的复现场景，在原始代码上其实**复现不出**所述症状

task.md 写：「容量为 2 时 `put(1); put(2); get(1); put(3)` 之后 `get(2)` 应返回 None，
实际却仍返回 2 的原值，而刚被访问过的 1 反而丢失」。

我按 task 目录里原始 `lru_cache.py` 的内容逐行重写后实测，该序列的实际行为是：

```
data = {1: 'a', 3: 'c'}   order = [1, 3]
get(2) -> None      （与 task.md 声称的“仍返回 2 的原值”不符）
get(1) -> 'a'       （1 确实保留了）
```

即**在这条特定序列上，原实现的结果恰好与正确 LRU 一致**。原因是两处缺陷在此序列中相互抵消：
`get(1)` 虽未刷新顺序，但淘汰端取的是队尾 `order[-1]`（= 2），刚好等于正确 LRU 该淘汰的 2。

所以我的结论是：**缺陷本身是真实存在的**（§3.2、§3.7 已用另一条序列证实「淘汰顺序反了、get 不刷新顺序」，
与 task.md 文字描述的语义完全一致），但 **task.md 里写的那条具体复现序列写错了**——
把 `get(1)` 换成 `get(2)` 才能观察到「刚被访问的 key 反而被丢、真正的 LRU key 反而留下」这一描述的症状。

我按文字描述的**语义**（严格 LRU：get 命中刷新顺序、淘汰最近最少使用）修复，
没有去迁就那条写错的序列；修复后该序列与正确的对称序列**都**通过（§3.1、§3.2）。

### 4.2 其余未覆盖项

- **非正容量**：`capacity <= 0` 时 `put()` 会抛 `IndexError: list index out of range`
  （容量 0 与 -1 实测均如此）。这是**修复前就存在**的行为（原实现是空列表上的 `order[-1]`，
  同样 `IndexError`），我**未改动**它——task.md 未把非正容量列为需求，
  且改动它会引入超出任务范围的行为约定。如需「容量 0 时 put 静默丢弃」，请明示。
- **并发**：`LRUCache` 无任何锁，多线程下 `data`/`order` 会失配。原设计即非线程安全，本次未涉及。
- **key 可哈希性 / `value` 为 `None`**：未做校验。注意 `get()` 用 `None` 表示未命中，
  因此**存入 `None` 值的 key 与未命中无法区分**——这是原接口的固有语义，非本次改动引入，也未修复。
- **`capacity` 很大 + 长时间运行**：`order` 与 `data` 均为 O(n) 结构，`remove`/`pop(0)` 是 O(n)；
  只是常数级性能问题，功能正确性不受影响，未做优化（避免超范围改动）。
