## 2. 做了什么

**单文件 `app.html`**，零外部依赖（无 CDN、无 `<link>`、无 `<script src>`、无 `fetch`/`XHR`/`import`，样式与逻辑全部内联）。

### 计算模型（分位精确）
1. 输入金额先规整到 2 位小数（四舍五入），再换算为整数「分」；
2. `基础份额 = floor(总分数 ÷ 人数)`；
3. 余下的 `R` 分，按顺序给前 `R` 人每人 +1 分；
4. **合计恒等于总金额**，相邻两人最多差 0.01 元。

核心函数 `splitBill(rawAmount, rawPeople)`（`app.html` 内 `/*__LOGIC_START__*/ … /*__LOGIC_END__*/` 段），返回值含 `ok / level / message / total / people / basePay / remainderCents / sharesCents / sumCents`，**内部全程 try/catch，永不向外抛异常**。

### 输入规整
`sanitizeNumeric()` 支持：全角数字/符号 → 半角、千分位逗号、空格/下划线、货币符号 `¥ ￥ $ € £`、单位「元/块」、前置 `+`。金额与人数分别用白名单正则校验后再 `Number()`（不用 `parseFloat`，避免 `"12abc"` 被截断成 `12`）。

### 交互反馈
- `input` / `change` 事件实时重算；
- 状态条三态配色：`ok`（绿）/ `warn`（黄，如金额被规整）/ `error`（红，如人数为 0）；
- 大号显示「每人应付」，下方明细表（人数 ≤ 30 时逐人列出，并给余数受益者打 `+0.01 余数` 标签；> 30 人则汇总展示）；
- 按钮：填入示例 / 重置 / 清空输入；
- 全局 `window.onerror` 兜底 + `render()` 自身 try/catch，异常只降级为一条提示，不白屏。

## 4. 不确定 / 局限

1. **未做真实浏览器渲染验证**：环境未启用浏览器自动化，UI 验证基于手写 DOM 桩（已验证逻辑接线与事件回调，但**未覆盖真实布局/样式呈现**）。建议人工开一次 `app.html` 目视确认。
2. **规整策略是「四舍五入」而非「截断」**：如业务方要求「不足 2 位小数直接截断」（例如 1234.567 → 1234.56），需改 `parseAmount` 中 `Math.round(v*100)/100` 一处。当前选择已在界面明确提示。
3. **人数硬上限 10 万、金额硬上限 1 万亿元**：超过即提示而非计算，避免明细表 DOM 过大；这些阈值是我自行设定的，非任务指定。
4. **负数金额一律拒绝**（未支持「退款/冲正」场景）；若需要负金额分摊需另行扩展。
5. **人数必须为整数**（`2.5 人` 报错）——任务只要求处理「0 或负数」，此处选择明确报错而非向下取整。
6. 随机守恒测试使用 `Math.random()`，每次运行样本不同；断言为性质断言（合计守恒、极差 ≤ 1 分），非固定快照。
