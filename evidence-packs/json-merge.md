# JSON 合并/对账+报告：历史致命缺陷模式清单（证据包 v1）

> 来源：P2 双臂实验 T7 四臂 fatal（机械判定台抓取，2026-09-15）。四件套格式；双向致命原则见 README。
> 可选参考，不构成验收标准。

## 统计口径族（本类任务历史最大坑）

### 1. stats 计数口径（duplicates / conflicts 的分界）
- **来源**：P2 round1 两臂自报 stats 相互矛盾（3/3/2 vs 3/3/1），oracle 判 A 臂 F1×3
- **双向致命**：把冲突条数错计入 duplicates（或反之）→ stats 整组错（漏报）；为了"对齐"改语义 → 与任务书定义不符（误伤）
- **自查输入**：构造既有同 id 同内容、又有同 id 不同内容的样例，手算 stats 后断言
- **检测思路**：任务书怎么定义就怎么实现；定义歧义处在 README 显式声明假设

### 2. 平局保留规则（A/B 同值冲突）
- **来源**：T7 判定台 probe，多臂反复出错
- **双向致命**：平局误判为冲突或丢行（漏报）；把真正的冲突当平局吞掉（也是漏报）
- **自查输入**：同 id 两文件同值的记录
- **检测思路**：比较在**规范化之后**进行（日期/金额先归一再比）

## 字段语义族

### 3. 日期格式归一
- **来源**：T7 判定台 probe_fmt_date（多臂 F3：误拒合法输入）
- **双向致命**：只支持一种写法 → 其它写法误拒（历史反复出现）；宽松到 `05/03/2025` 也猜 → 歧义错配
- **自查输入**：`2025-01-02`、`2025.01.02`、`20250102`、`05/03/2025` 各一次
- **检测思路**：支持的写法白名单化；歧义格式显式报错而非猜

### 4. 金额缺失 / null / 千分位
- **双向致命**：null 金额静默变 0.0 → 统计污染（F1）；把 null 报成错误 → 任务书允许 null 时误拒
- **自查输入**：金额为 null、缺失键、`"1,234.5"`
- **检测思路**：三种输入分别有明确行为并在 README 声明

### 5. 同文件内重复 id
- **双向致命**：只查跨文件重复 → 文件内重复漏掉；把合法的文件内重复当错误
- **自查输入**：单文件内两行同 id
- **检测思路**：去重/合并规则同样作用于文件内

## 输出族

### 6. reconciliation.html 注入（F2）
- **自查输入**：订单字段含 `<script>`、`</textarea>`、`<img>`
- **检测思路**：全部动态字段 html.escape，断言输出含原中文文本

### 7. 输出编码与确定性
- **双向致命**：GBK 或带 BOM → 消费端损坏（F1）；不确定性排序 → 同输入两次运行结果不同（难以审计）
- **自查输入**：跑两次 diff 输出；`file`/字节检查 UTF-8 无 BOM
- **检测思路**：排序键固定；写文件显式 `encoding="utf-8"`

### 8. validate.py 有鉴别力
- **来源**：P1-7 五面病理 §8——"校验器永远通过"是历史真实缺陷
- **双向致命**：校验器对损坏输入也 PASS → 等于没有；对合法输出误报 → 不可用
- **自查输入**：对 merged.json 做 2-3 种篡改（改数值/删字段/改编码）确认 validate 全部变红
- **检测思路**：变异自查——故意改坏实现，validate 必须跟着红
