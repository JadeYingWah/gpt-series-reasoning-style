## How It Works / 工作原理：一忘一想，五面时序

整个 skill 的节奏是**忘与想的交替**：`忘 → 想 → 忘 → 继续忘 → 想`。

```text
┌─ 规划面1（自由构想，忘记skill）
│    先彻底忘记这个skill的存在——这一遍靠的是你的判断力，不是规则。
│    想清楚了，再进入规划面2。
│         ↓
┌─ 规划面2（规则规划，重新想起skill）
│    重新想起skill，按下面的规则把上一步想清楚的落成计划。
│    这一面要过 7 件事（见下），过完才动工。
│         ↓
┌─ 执行面（彻底忘记skill）
│    规划做完了就开始干活——就像你从来没加载过它一样。
│    怎么写、怎么想、怎么调试，全靠你自己的能力，纪律不打断思路。
│    唯一的触发点：当你觉得「我做完了」的时候，进入审查面1。
│         ↓
┌─ 审查面1（直觉检查，继续忘记skill）
│    还是彻底忘记skill，用直觉和常识检查一遍：
│    有没有哪里不对？有没有哪里漏了？规则没覆盖到的问题，这一遍抓。
│         ↓
└─ 审查面2（纪律检查，重新想起skill）
     重新想起skill，严格过一遍七条纪律（见下），确保规则覆盖到的问题都做到了。
```

### 为什么是"两个规划面 + 两道审查"

| 面 | 状态 | 抓什么 |
|---|---|---|
| 规划面1 | 忘记 | —（自由构想，先不被纪律框住） |
| 规划面2 | 想起 | 想清楚之后，规则才上——纪律不污染思路（1.4.47 起） |
| 执行面 | 忘记 | —（创作是创作） |
| 审查面1 | 继续忘记 | 规则**没覆盖到**的问题，靠直觉抓 |
| 审查面2 | 想起 | 规则**覆盖到**的问题，靠纪律确保做到 |

**核心设计：创作是创作，检查是检查。** 规则推迟到"想清楚之后"才上；检查分直觉与纪律两道，互不替代。

## 规划面2 的七件事 / planning checklist

进入规划面2 后，把构想落成计划时过这 7 件事：

1. **形态判断自己心里做**——不要输出思考过程，不要跟用户说"我选择形态一/二/三"，直接干活。
2. **协作形态可叠加**：同一个任务可以自己干一部分（形态一）、派子Agent干一部分（形态二）、协调外部模型干一部分（形态三）。默认从形态一起步，哪部分需要并行/独立/跨模型就叠加哪个。
3. **轻量档**：只做分工方案、不实际派发时，不建 `_agents/` 目录、不写任务包文件；方案获批准后再展开。
4. **小且可逆 = 指令即授权**：直接做、别请示；只有不可逆、对外发布、删东西才事前确认。
5. **按风险分级**：规划时就判断——轻任务只做 3 条纪律（真打开看一眼 / 未验证标注 / 防死循环）；数据/代码/多Agent 类重任务做全 7 条。
6. **动手前先调研**：重任务先花几分钟查网上怎么做、有什么坑、有没有最佳实践，不要凭感觉瞎写。
7. **最后确认档位**：跟用户确认这次怎么沟通——**A 档**一次性确认（推荐方案列出，同意就开干）或 **B 档**逐项问答（一次一个最高影响问题）。用户没说就默认 A 档。

## Rules / 七条纪律

审查面2 严格过这 7 条（顺序与 `SKILL.md` 一致；★ = 轻任务也必须做的 3 条）：

| # | 纪律 | 要点 |
|---|---|---|
| 1★ | **真打开看一眼** | 产物在真实环境打开、真用一遍——HTML 要浏览器渲染、API 要前端调，跑脚本不算。环境不支持时：如实标"未验证：浏览器渲染"+ 给用户自验步骤 |
| 2★ | **未验证标注** | 交付只说三件：做了什么 / 怎么验的（给可复现命令）/ 哪些没验。没验的逐条列原因，不许只写"部分未验证" |
| 3 | **失败两次换路** | 同一动作连续失败第 2 次，禁止同法第 3 次；先判断是否与已验路径等价，别死磕 |
| 4 | **全绿不算证据** | 把要防的错误故意做一次，断言红才算验过；变异后照样全绿 = 变异没生效。最小菜谱：每个写入口至少打 空值/超长/非法类型/缺键 |
| 5 | **关键数字重算** | 数据/研究类交付的关键数字，独立方法重算或双源交叉；对不上以重算为准 |
| 6 | **临时物隔离** | 临时文件不进交付目录、收尾清掉；清理只动本任务自己的目录，禁全局杀进程 |
| 7★ | **防死循环** | 同一文件连读 3 次无新信息就停；同一动作连续 3 次输出相同就换思路 |

**★ = 233 次实验沉淀下来的核心条款——"规则越少越好，但核心那几条不能少"的那几条。**

## 多智能体协作 / 形态二三

细则在 `references/multi-agent.md`（命中才读），模板在 `templates/`。

### 形态二 · 子智能体（有明显增益就自觉开，不等用户说）

**命中任一就开**：完全独立的子活 / 要并行跑两件事 / 要独立挑刺视角 / 中间过程怕污染主上下文。
派发给清三样：**目标、完成标准、交回给谁**。铁律：子智能体交回后**主 Agent 仍是 DRI**，必须自己验收；子智能体不直接对用户；一个人能连贯干完的事不开二。

### 形态三 · 多智能体（用户指名 / 跨模型 / 大任务分工）

六步：指挥官身份声明 → 建立角色档案 → 拆子任务写任务包 → 用户转述派发 → 对照原始目标验收（先查跑偏，再交审查者挑刺）→ 向用户汇报三件套。

**任务包七要素**：背景 / 已定决策 / 未定缺口 / 完成标准 / 允许与禁止范围 / 唯一 DRI / 交回给谁。

**三个角色卡**（`templates/`）：**指挥官**默认 DRI，委派不转移最终责任；**执行者**只说"按标准做完了，请验收"；**审查者**独立挑刺、不亲自改活。
**红线**：执行者说「我做完了」不算验收；审查者不亲自改；不绕开指挥官直接汇报。

## Field Tests / 实测与证据

这个 skill 的每一次删减与保留，都是 A/B 实验投出来的票。**累计 233 次实验**：

| 阶段 | 版本 | 实验次数 | 结论 |
|---|---|---|---|
| v1.2.x 重版本 | 3043 个文件 / 179 行 | **207 次** | **规则越多效果越差** |
| v1.4.x 极简版 | 6 个文件 / 59 行（实测） | **26 次** | **有用，且无负面影响** |

**233 次实验最终证明的四件事：**

1. **重版本是错的**——规则越多效果越差，207 次实验证明了。
2. **极简版是对的**——59 行，有用，没副作用，26 次实验证明了。
3. **核心价值是真的**——「真打开看一眼」「未验证标注」，这几条是真有用。
4. **没有负面影响**——轻任务上价值小，但也没坏处。

> **233 次实验测出来的不是"规则越多越好"，而是"规则越少越好，但核心那几条不能少"。**
> 这就是这个 skill 最值钱的地方——**它是被 200 多次实验证明"做减法"的那个。**

## When To Use / 何时使用

**推荐用：** 代码交付 · 数字验算 · 数据报告 · 视觉产物 · 多 Agent 协作 · 任何"声称完成就要对产物负责"的场景。

**不用：** 一句话问答 · 探索性草稿 · 纯聊天 · 无人验收的内部实验 · 小且可逆的改动（指令即授权，直接做）。

**边界**：只改完成任务必须改的地方；发现会让交付物坏着交的问题顺手修掉，其余不碰。
